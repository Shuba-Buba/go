# versions — какую цену выберет Go

Команда строит короткий отчёт. `cart` считает цену двух упаковок чая,
`report` показывает цену одной. Оба используют модуль `catalog`,
но требуют разные версии. Все версии лежат в локальном `../proxy`.

Из `versions/` подготовьте загрузку учебных модулей:

```shell
export GOWORK=off
# Linux/macOS
export GOPROXY="file://$(cd ../proxy && pwd)"
# Windows, Git Bash: вместо предыдущей строки
# export GOPROXY="file:///$(cd ../proxy && pwd -W)"
```

Цена одной упаковки в подготовленных версиях `catalog`:

| Версия | Цена |
| --- | --- |
| v1.0.0 | 100 |
| v1.1.0 | 110 |
| v1.2.0 | 120 |

## Сначала прогноз

Прочитайте свой `go.mod` и файлы требований зависимостей:

```shell
cat ../proxy/example.org/workshop/cart/@v/v1.0.0.mod
cat ../proxy/example.org/workshop/report/@v/v1.0.0.mod
```

До запуска запишите:

- какую версию `catalog` выберет Go для всего проекта;
- могут ли `cart` и `report` одновременно использовать разные версии
  одного пути модуля;
- какую цену получит каждый из них.

`go mod graph` печатает граф требований: строка `A@v1.0.0 B@v1.1.0`
означает, что версия 1.0.0 модуля A требует B версии 1.1.0.
У основного модуля слева версия не указана; строки про `go` и `toolchain`
описывают требования к версии Go.

Теперь проверьте прогноз и объясните каждое ребро графа:

```shell
go list -m all
go mod graph
go run .
go test ./...
```

## Измените граф, а не исходники

1. В `go.mod` основного модуля явно задайте для `catalog` требование `v1.0.0`
   командой `go mod edit -require=example.org/workshop/catalog@v1.0.0`.
   Запустите `go mod tidy`, затем `go list -m all` и `go run .`.
   Снизилась ли выбранная версия? Что `tidy` вернул в `go.mod`?
   Какое ребро объясняет наблюдение?
2. Поднимите выбранную версию `catalog` до `v1.2.0` командой управления
   зависимостями. Исходники `cart`, `report` и приложения менять не нужно.
   Доступные версии: `go list -m -versions example.org/workshop/catalog`.
3. Сравните `go.mod` и `go.sum` до и после `go mod tidy`.
   Назовите файл требований и файл контрольных сумм; объясните, почему
   появление нескольких версий в `go.sum` не означает их совместную сборку.

В итоговом `go.mod` приложение должно требовать `catalog v1.2.0`,
`cart v1.0.0` и `report v1.0.0`. В графе могут оставаться требования
старых версий; это не конфликт и не причина редактировать чужие модули.

## Проверка результата

```shell
go list -m all
go run .
go test ./...
```

В итоговом выводе должна быть версия `v1.2.0`; цена корзины должна быть
вдвое больше цены отчёта. Объясните, какую зависимость пришлось бы изменить,
если нужно было бы выбрать `catalog v1.0.0`, не меняя исходники потребителей.
