# Семинар 7: как собрать и воспроизвести Go-проект

В четырёх лабораторных печатаем чек с ценой чая. Вычисления уже написаны:
сегодня меняем устройство проекта и способ выбора зависимостей.

1. [packages](packages/README.md): выделить пакет и собрать две команды.
2. [workspace](workspace/README.md): связать два локальных модуля двумя способами.
3. [versions](versions/README.md): предсказать и изменить выбранную версию.
4. [vendor](vendor/README.md): диагностировать устаревшую копию зависимостей.

Нужен Go 1.27.0 или совместимый более новый Go. Проверьте `go version`.
Если установлен более старый Go, сначала выберите toolchain курса;
директивы `go` в заданиях не понижайте.

Из этого каталога подготовьте окружение текущего терминала:

```shell
export GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local
unset GOWORK
# Linux/macOS
export GOMODCACHE="$(mktemp -d)"
export GOCACHE="$(mktemp -d)"
```

В Windows используйте Git Bash и вместо последних двух строк задайте
пути в формате, который понимает Windows Go:

```shell
export GOMODCACHE="$(cygpath -m "$(mktemp -d)")"
export GOCACHE="$(cygpath -m "$(mktemp -d)")"
```

Это временные каталоги; пользовательский кеш не меняется. `GOSUMDB=off`
нужен для учебных версий `example.org`, которых нет в публичном sumdb.
Для публичных зависимостей обычного проекта оставляйте проверку sumdb включённой.
`go.sum` продолжает хранить контрольные суммы загруженных файлов.

Выполняйте команды внутри указанной лабораторной или её модуля.
Общий `go test ./...` из этого каталога не обходит вложенные модули.
`proxy/` — готовые учебные версии в формате Go module proxy;
не редактируйте и не распаковывайте их при решении.

Шаблоны `packages` и `versions` собираются сразу. В `workspace/app` пока
не связан локальный модуль, а в `vendor` намеренно разошлись `go.mod` и
`vendor/modules.txt`. Их сообщения об ошибке — исходные данные задач.
