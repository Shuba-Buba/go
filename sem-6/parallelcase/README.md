# parallelcase: fixture и параллельные подтесты

В `lifecycle_test.go` есть реальный тест: два подтеста читают один файл.
Он использует только готовый пакет `testing`, но сейчас освобождает ресурс
слишком рано. Предскажите порядок событий, запустите тест и исправьте
время жизни файла. Проверки и `t.Parallel()` должны сохраниться.

Нужные правила:

- `t.Run(name, fn)` запускает подтест и ждёт его завершения **или** вызова
  им `t.Parallel()`.
- `t.Parallel()` приостанавливает подтест. Его оставшаяся часть продолжится,
  когда функция родительского теста вернётся.
- Завершение родительской функции и завершение всего родительского теста —
  разные события: тест ждёт своих подтестов, затем запускает cleanup.
- `defer` родительской функции срабатывает при её возврате. `t.Cleanup`
  этого родителя ждёт завершения его подтестов.

Буферизированный канал `events` — журнал: отправка добавляет событие,
а после завершения группы тест читает все записи. Ёмкости хватает на четыре
события. Канал не задаёт порядок двух читателей; оба допустимых порядка
проходят проверку. Sleep и предположения о расписании не нужны.

`os.WriteFile(path, data, perm)` записывает файл; `os.ReadFile(path)` читает
его целиком. Каталог из `t.TempDir()` автоматически удаляется после теста.
Сам файл здесь освобождается отдельно, чтобы увидеть ошибку времени жизни.

```shell
go test -v ./parallelcase
go test -race ./parallelcase
```

Происхождение: новый сценарий с общим входным файлом и журналом событий.
Он продолжает тему fixture из `testcleanup`. Мост к бонусному `tparallel`:
видны остановка в `Parallel`, возврат родительской функции и завершение
группы. Собственный планировщик, API `T` и его состояние здесь не реализуются.
